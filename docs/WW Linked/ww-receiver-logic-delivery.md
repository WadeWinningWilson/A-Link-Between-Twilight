# Delivering WW receiver LOGIC through the plugin — the actor class

**Lane:** Bridge (acting: History/Engine — real Bridge unreachable, user 2026-08-14)
**Status:** design, evidence-backed, nothing landed. Answers the §939 clarification's open
job — *"deliver existing receiver logic via the plugin, since the proven mod shape ships
DATA only"* — for the largest and best-evidenced class: **actors**.

**Scope discipline.** The clean-room run (§933/§955) proved the donor-ACCESS half ships
zero-change. This document is about the other half. It plans no code; the gates forbid new
`files.cmake` entries and new native seams, and nothing here needs either to be *decided*.

---

## 1. What an actor actually requires from the receiver

Taken from the nine actors I have landed (tsubo, Jb1, shelf, paper, plant, lwood, npc_p1,
tag_kb_item, tag_so), not from theory. Three registration touchpoints, plus a link surface
nobody had enumerated:

| Need | Today (in-exe) | Plugin route | Verified |
|---|---|---|---|
| proc name | `fpcNm_*` enum row (`f_pc_name.h`, NATIVE) | none needed — `fpcPf_Get(s16)` takes an opaque index | §949 |
| profile lookup | `g_fpcPfLst_ProfileList` slot (`f_pc_profile_lst.cpp`, NATIVE) | hook `fpcPf_Get`; the WW lookup already runs FIRST and returns before the table | §949 |
| placement route | `OBJNAME` row (`d_stage.cpp`, NATIVE) | pre-hook `dStage_searchName`/`getName`; declare stages via `dBootStage_add` | §947 / §956 |
| **link surface** | direct calls — same binary | **by-name runtime resolution** off the exe's own export table (31,975 exports, 2,567 `DATA`) — no implib, no import thunk, no native edit | §965 (§2) |

The first three are Foundry's §947 result, which I verified at source. The fourth is the
one nobody had stated, and it is where the real work is.

## 2. The link surface — the finding that reshapes the estimate

`ww_donor_disc` ships with **no** `FEATURES game` and its header says so plainly: *"Services
only … it links against nothing of the exe."* That is why it runs on a stock exe unchanged
— and it is also why it is **not** a template for an actor. An actor calls receiver
internals constantly.

The SDK already supports the harder case. `add_mod(... FEATURES game ...)` sets
`_needs_host_link`, and on Windows (`cmake/ModSDK.cmake:235`):

> *"Mods link against the game's import library (`sdk/windows-<arch>.lib`, generated by
> `setup_windows_exports`) … **Function calls resolve through import thunks; game data is
> reachable only through `__declspec(dllimport)`, i.e. `DUSK_GAME_DATA`-annotated
> declarations.**"*

**So the split is: functions are free, DATA is not.** And `include/global.h:118` is candid
about how far that has gone — *"Only declarations a native mod actually references are
annotated in this tree so far."* The whole tree currently carries **3** `DUSK_GAME_DATA`
uses.

### The concrete consequence for actors

Every actor profile I have written ends with the same two references:

```c
&g_fpcLf_Method.base,   // include/f_pc/f_pc_leaf.h:47  — plain extern
&g_fopAc_Method.base,   // include/f_op/f_op_actor.h:434 — plain extern
```

Neither is annotated. `dComIfGp_*` accessors are worse in kind, not in count: many are
**inline functions over `g_dComIfG_gameInfo`** (`d_com_inf_game.h:1065`), so an innocuous
call like `dComIfGp_getStartStageName()` compiles into a direct read of game data at the
mod's call site. `g_dComIfG_gameInfo` *is* annotated (`DUSK_GAME_EXTERN`) — which is
exactly the precedent proving the mechanism works and simply has not been swept.

**REVISED — there are TWO routes, and the annotation sweep is the WORSE one (§965).**
Measured against the generated export table
(`build/windows-msvc-relwithdebinfo/dusklight_exports.def`): **31,975 exports, 2,567 of
them marked `DATA` — and all three symbols an actor needs are already there**:

```
?g_dComIfG_gameInfo@@3VdComIfG_inf_c@@A   DATA
?g_fopAc_Method@@3Uactor_method_class@@A  DATA
?g_fpcLf_Method@@3Uleafdraw_method_class@@B DATA
```

So the data is EXPORTED already; `DUSK_GAME_DATA` is only what lets the **compiler** emit an
indirect load for the LINK-TIME import path. That gives two options:

- **(a) Link-time import** — `FEATURES game` + implib, requires annotating each referenced
  declaration. **These are NATIVE headers (`f_op_actor.h`, `f_pc_leaf.h`, …), so this route
  is currently FORBIDDEN by the §939 gates.** It also re-couples the mod to a build.
- **(b) Runtime by-name resolution** — what the §964 hook smoke already demonstrated on the
  vanilla exe, with **no import thunk into `dusklight.exe` at all**. Needs **zero** native
  edits, because the symbols are already in the `.def`.

**Route (b) is the design.** Its one real consequence for port shape: an actor's
`actor_process_profile_definition` can no longer be a static initializer referencing
`&g_fopAc_Method` — the profile must be **filled in at mod-init from resolved addresses**.
That is a mechanical transformation of the nine profile blocks I have written, entirely
WW-side, and it is gate-legal today.

## 3. The one genuine obstruction

`DMC[fpcNm_MAX_NUM]` (`c_dylink.cpp:807`) is indexed **unguarded** by proc name in
`cDyl_IsLinked`/`Unlink`/`LinkASync`, and it sits on the create path
(`fpcFCtRq_Request` → `fpcLd_Use` → `fpcLd_IsLoaded` → `cDyl_IsLinked`). So the move that
§1's row 1 unlocks — *plugin picks indices above the enum so the native enum never grows* —
would read past a static array on every plugin-actor spawn. One bounds check in those three
accessors, answering "not linked" out of range (which is true for a plugin actor), makes
the enum genuinely optional. **This is the single line the whole shape depends on.** (§949.)

---

## 4. Proposed sequence

1. **Guard `cDyl_*`** (one line ×3). Decides whether the enum is optional. — *f_pc owner*
   *(NOTE: `cDyl_IsLinked` is itself exported, so this could alternatively be HOOKED
   mod-side rather than patched — which would make even this step gate-legal.)*
2. **Runtime-resolve the three data symbols** and build the profile at mod-init. No native
   edit. Done when a mod resolves all three and constructs a valid profile. — *Bridge*
3. **Three hooks**: `fpcPf_Get` and `dStage_searchName`/`getName` are both exported and
   hookable by the proven §964 path. **`dBootStage_add` is NOT in the export table (0 hits)
   — the routing leg has no by-name entry point today**, and that is now the sharpest
   remaining question for the routing half. — *Foundry/Bridge*
4. **Move one actor** as the pilot. `tag_so` is the right choice: smallest surface, no model,
   no collision, no message flow — it tests registration and linkage and nothing else.
5. Only then the rest of the family.

**Falsifiable checkpoint at step 4:** if a mod carrying `tag_so` — built on the §964
by-name shape, NOT `FEATURES game` — loads, resolves its three data symbols, registers
through the hooked `fpcPf_Get`, and its zone tag is found by a search on a **stock** exe,
the actor class is proven mod-side. If it fails, it fails at a named step, not vaguely.

## 5. What this does not cover

Actors are one class. Untouched here, and each needs its own pass: the kankyo/lighting
feeders, the event-system seams I edited in native files (`d_stage`, `d_com_inf_game`,
`d_event_manager`, `d_event_data`), and the particle/JPA lane. **The seams are the harder
half** — a hook replaces a call, but several of my edits *insert* behaviour mid-function
(the §901 WW branch inside `getEventName`, the §892 layer resolution inside
`getLayerNo_common_common`). Those have no single choke point to attach to and are the
genuine Tier-2 unknown. I am not claiming a route for them here.
